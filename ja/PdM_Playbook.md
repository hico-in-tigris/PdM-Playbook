# PdM Playbook
**ユーザー理解からプロダクト実装までの実践ガイド**

---

## はじめに

このPlaybookは、PdMとして現場で経験してきたことを整理した実践ガイドです。各Partは「何をするか・なぜするか」の概要を示しています。実際の手順や問いのパターンは、末尾のSkillsに実装されています。Playbookを地図として使い、Skillsを道具として使うものです。

---

## Part 1｜PdMの役割

PdMの仕事は**ループを回すこと**です。ユーザー理解 → 問題定義 → 仮説 → 意思決定 → 実行 → 学習。このサイクルを高速・高精度で回し続けることがすべてです。

**責任範囲**: 問題定義・優先順位・プロダクト方向性  
**やらないこと**: 実装の細部管理・すべての意思決定

---

## Part 2｜ユーザー理解（Observe）

**Hear（聞く）→ See（見る）→ Do（やってみる）** の3段階で深めます。インタビューだけでは不十分で、現場に出て、ユーザーと同じ作業を体験して初めて見えるものがあります。

観察で捕まえるべきもの: 作業フロー・Workaround・感情・非効率。特にWorkaroundは問題の深刻さを示すサインです。

**AIにできないこと**: ユーザーの現場観察はAIには代替できません。CSチケットやヒアリングメモの整理はAIが得意ですが、「なぜそのWorkaroundが生まれたか」の背景理解は、実際に現場を見た人間にしか持てない文脈です。

> 🔧 **Skill 1｜pdm-voice-to-problem** — CSチケット・問い合わせ・ヒアリングから問題定義を抽出する

---

## Part 3｜問題定義（Orient）

ユーザーの**要望**と**問題**は別物です。「CSVを速くしてほしい」は要望であり、「進捗が見えない不安」が問題です。要望をそのまま解こうとすると、正しく作っても意味がないものができます。

「なぜ？」を繰り返して本質に辿り着くことが重要です。問題定義への投資を惜しまないようにしましょう。

> 🔧 **Skill 1｜pdm-voice-to-problem** — 声を問題定義に変換する  
> 🔧 **Skill 2｜pdm-discuss-to-designdoc** — AIディスカッションで問題を整理する

---

## Part 4｜仮説思考

問題が定義できたら仮説を立てます。**問題 → 原因仮説 → 解決仮説** の三層で構造化します。仮説を明文化することで、検証の計画が立てられ、関係者と共有でき、後から学習できます。

良い仮説の条件: シンプル・検証可能・ユーザー価値に繋がっていること。

> 🔧 **Skill 2｜pdm-discuss-to-designdoc** — AIとのディスカッションで仮説を構造化する

---

## Part 5｜意思決定

PdMの最重要仕事です。情報が常に不完全な中で判断し、前に進めます。優先順位の実態は「やらないことを決めること」です。

判断軸は**Impact × Effort × 戦略整合性**の三軸で評価します。Impact・Effortだけで優先順位を決めると、今クォーターの会社の方向性と合わない機能に工数を使うことになります。「高Impactだが、今の戦略上やるべきではない」という判断ができることがPdMの成熟度を示します。

決断を先送りするコストは、間違えるコストより大きいことを忘れてはいけません。

> 🔧 **Skill 5｜pdm-priority-matrix** — Impact × Effort × 戦略整合性で優先順位を整理する  
> 🔧 **Skill 6｜pdm-scope-management** — Must/Should/Could/Won'tでスコープを合意する

---

## Part 6｜ステークホルダーマネジメント（Align）

**良いドキュメントは、読まれなければ存在しないのと同じです。**

PdMが作るDesign Doc・仕様書・優先順位マトリクスは、関係者に理解・合意されて初めて機能します。このAlignフェーズはOODAループに並走する継続的な活動であり、後回しにできるものではありません。

### ステークホルダーの種類と接し方

| 種類 | 主な関心 | PdMがやること |
|---|---|---|
| 経営層・上位職 | ビジネス価値・ROI・戦略整合 | 問題とインパクトを数字で語る。実装の話は後回し |
| エンジニア | 実現可能性・技術負債・仕様の明確さ | 曖昧さをなくす。変更の理由を伝える。Open Questionsを一緒に潰す |
| デザイナー | ユーザー体験・一貫性 | 問題定義の段階から巻き込む。答えを持ち込まない |
| セールス・CS | 顧客への約束・納期・機能リスト | 「いつ何ができるか」だけでなく「なぜそれをやるか」を伝える |

### 合意の取り方

合意には段階があります。すべての関係者が全情報を持つ必要はありませんが、各自が「自分の領域で何が決まったか」を知っている状態を作ることが目的です。

- **問題定義の合意**: Design Docのレビュー前に「このProblem認識は正しいか」を確認する
- **優先順位の合意**: マトリクスを一人で作って持ち込まない。評価軸の定義を関係者と事前に揃える
- **スコープの合意**: Won'tリストを明示し、「入っていない」ことを事前に伝える
- **仕様の合意**: Open Questionsを潰すアクションを誰が持つか明示する

### 反対意見への向き合い方

反対意見は情報です。「なぜ反対しているか」の背景を理解すると、問題定義の見直しにつながることがあります。

- 反論をつぶすのではなく、背景にある懸念を言語化する
- 「今回はやらない理由」を丁寧に説明できるようにしておく
- 合意できない場合は判断の根拠と責任の所在を明確にして前に進む

## Part 7｜実行（Act）

PdMは実装しませんが、開発チームが最速で動ける状態を作ります。ユーザーストーリーで「誰のための機能か」を明確にし、仕様で曖昧さをなくし、モックで認識のズレを事前に解消します。

> 🔧 **Skill 3｜pdm-designdoc-to-spec** — Design Doc → 仕様書  
> 🔧 **Skill 4｜pdm-spec-to-prompt** — 仕様書 → AI実装指示プロンプト

---

## Part 8｜学習ループ（Learn）

リリースはゴールではなくチェックポイントです。学習ループを回すには、**計測設計をリリース前に終わらせておくこと**が必須です。リリース後に「何を見ればいいか」を考え始めても遅い。

### 計測の二層構造

**定量（What）**: 何が起きているかを把握する

| 計測の種類 | 問い | 例 |
|---|---|---|
| 採用率 | 機能を使っているか | 7日以内に1回以上使ったユーザー率 |
| 継続率 | 使い続けているか | 4週後のリテンション |
| 完了率 | 目的を達成できているか | フローの最終ステップ到達率 |
| エラー率 | どこで詰まっているか | エラー発生ステップの分布 |

**定性（Why）**: なぜそれが起きているかを理解する

- 数字が想定外のときにのみ調査するのではなく、リリース後2週間以内に最低2〜3人のユーザーに使用感を聞く
- 「使いにくかった箇所はどこか」より「何を達成しようとしてどう動いたか」を聞く

### 仮説と結果の照合

リリースのたびに以下を記録します。

```
仮説: [誰が][何をすることで][どんな指標が][どう変わると予測したか]
結果: [実際に何が起きたか]
学習: [仮説のどこが正しく・どこが間違っていたか]
次の問い: [このリリースから生まれた新しい疑問は何か]
```

この記録が次のObserveになります。記録がないと、組織として同じ仮説を何度も立て直すことになります。

### 計測しない判断も意思決定

すべての機能を数字で評価できるわけではありません。データが取れない領域・取るコストが見合わない領域では、「計測しないと決める」ことも意思決定です。その場合は「なぜ計測しないか」を明示しておきます。

## Part 9｜PdM思考フレーム（OODA + Align）

全体を統合するフレームワークです。

| フェーズ | 内容 |
|---|---|
| **Observe** | ユーザー理解・現場観察 |
| **Orient** | 問題定義・仮説構築 |
| **Decide** | 優先順位・意思決定（戦略整合性を含む） |
| **Act** | 実行・リリース |
| **Learn** | 計測・仮説照合・次のObserveへ |
| **Align** | 全フェーズに並走。ステークホルダーとの認識合わせ |

AlignはOODAループの「外側」に位置するのではなく、各フェーズで常に行われます。Observeの段階で「この問題定義で経営層は納得するか」を考え、Decideの段階で「この優先順位をエンジニアはどう受け取るか」を考えることがAlignです。

このループを止めない限り、プロダクトは進化し続けます。

## Part 10｜AI時代のPdM

AIはループを速くする道具です。**アイデア → AIディスカッション → Design Doc → 仕様書 → 指示プロンプト → プロトタイプ** のフローで、コードを書かずに仮説検証ができます。

### AIが得意なこと・苦手なこと

PdMとしてAIを使いこなすには、AIの能力の境界を正確に知っておく必要があります。

| AIが得意なこと | 人間が担うべきこと |
|---|---|
| 声・テキストの分類・整理 | 現場観察・ユーザーとの対話 |
| 構造化（テンプレートへの変換） | 市場環境・競合動向の文脈理解 |
| 内部ロジックの整合性チェック | 組織の政治・関係者の感情の読み取り |
| エッジケースの列挙 | 「何が本当に重要か」の価値判断 |
| 仕様書・プロンプトの生成 | 最終的な意思決定と説明責任 |

**特に注意**: AIとのディスカッションは「内部ロジックを整理する」のに強力ですが、AIは市場の現実・自社の状況・組織の文脈を知りません。これらの情報は人間が持ち込む必要があります。「AIと話せば市場調査は不要」は誤りです。

変わらないのは問題定義力と判断力、変わるのは実装スピードです。新たに求められるのは言語化力・評価力・AIへの適切な委譲判断です。

> 🔧 **Skill 1〜4** がこのフロー全体をカバーします

---

## Part 11｜PdMの成長

経験は積むだけでは意味がありません。**消化して初めて成長になります**。

成長を加速する5つの習慣:
1. 週1回ユーザーを見る
2. すべての機能開発に仮説を書く
3. 迷っても決断する
4. リリース後に仮説と結果を照合する
5. ステークホルダーとの摩擦を記録し、パターンを見つける

---

## Part 12｜PdM Toolkit

PdMの実務を支える道具一式です。思考のフレームワークとAI Skillsを組み合わせて使います。

### Problem — 問題を定義する

| ツール | 概要 |
|---|---|
| ユーザー理解メモ | 観察・インタビューで得た声を「見たこと・聞いたこと・気づき・問い」の4欄で即記録する |
| 問題定義テンプレ | 誰の・どんな問題か・インパクト・スコープを1枚に整理する |
| 仮説テンプレ | 問題 → 原因仮説 → 解決仮説の三層を明文化する |

> 🔧 **Skill 1｜pdm-voice-to-problem**  
> CSチケット・問い合わせ・ヒアリング内容をインプットに、ユーザーの声を分類・整理し、問題定義サマリーを出力します。Skill 2へそのまま渡せる状態にします。

### Design — 設計する

| ツール | 概要 |
|---|---|
| Design Doc | Background / Problem / Goals / Non-Goals / User Story / UX Flow / Technical Notes / Metrics の8セクションで構成。「何を・誰のために・なぜ作るか」を関係者で共有するための中心ドキュメントです |

> 🔧 **Skill 2｜pdm-discuss-to-designdoc**  
> アイデアや問題定義サマリーをインプットに、AIとのディスカッションを通じて思考を整理し、Design Docを生成します。

### Build — 実装に渡す

| ツール | 概要 |
|---|---|
| 仕様書 | ハッピーパス・エッジケース・表示状態・やらないことを明文化したエンジニア向け実装指示書 |
| 指示プロンプト | Goal / Tech / Requirement / Output の4層で構成するAIへの実装指示。そのままAIに渡してプロトタイプを生成できます |

> 🔧 **Skill 3｜pdm-designdoc-to-spec**  
> Design Docをインプットにエンジニアがそのまま実装に使える仕様書を生成します。エッジケース・表示状態の漏れも検出します。

> 🔧 **Skill 4｜pdm-spec-to-prompt**  
> 仕様書をインプットにAIへの実装指示プロンプトを生成します。コードを書かずにプロトタイプを得るための最終ステップです。

### Decision — 意思決定する

| ツール | 概要 |
|---|---|
| 優先順位マトリクス | Impact × Effort × 戦略整合性の三軸で機能・施策を評価し「優先する・計画する・余裕があれば・やらない」に分類する |
| スコープ管理 | Must / Should / Could / Won'tでリリーススコープを定義する。Won'tを明示することがスコープクリープを防ぐ |

> 🔧 **Skill 5｜pdm-priority-matrix**  
> 機能・施策リストをImpact × Effort × 戦略整合性で評価し、優先順位表と推奨アクション順を出力します。

> 🔧 **Skill 6｜pdm-scope-management**  
> Must / Should / Could / Won'tでスコープを定義し、合意できるスコープ定義表を出力します。

### Learn — 計測・学習する

| ツール | 概要 |
|---|---|
| 計測設計シート | リリース前に「何を・なぜ・どう計測するか」を定義する。採用率・継続率・完了率・エラー率の4指標を基本セットとする |
| 仮説照合ログ | 仮説・結果・学習・次の問いの4項目を記録する。組織の学習資産になる |
