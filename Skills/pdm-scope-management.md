# Skill 5｜スコープ管理

## このSkillの目的

リリースや開発サイクルのスコープを**Must / Should / Could / Won't**（MoSCoW法）で整理し、「何をやって何をやらないか」を明確に合意できる状態にします。

**インプット**: 機能・要件のリスト、または優先順位マトリクス（Skill 4の出力）  
**アウトプット**: スコープ定義表＋Won'tリスト（明示的なスコープ外）

---

## 実行手順

### Step 1｜スコープ整理の前提確認

スコープを決める前に、以下を確認します。

- **対象リリースはいつか**（期日・スプリント期間）
- **利用可能なリソースはどのくらいか**（エンジニア人数・稼働週数）
- **Skill 4（優先順位マトリクス）の結果はあるか**（あればそれを土台にする）

リソースが不明な場合は「このリリースで何週間・何人で動くか」を確認してから進めます。

---

### Step 2｜各項目の分類

以下の基準でリストの各項目をMust / Should / Could / Won'tに分類します。

```
Must（必須）
  このリリースで必ず届けなければならないもの。
  これがなければリリース自体の意味がなくなる。
  → 全体の50〜60%以内に収めるのが目安。

Should（重要）
  できれば入れたいが、Mustほど絶対ではないもの。
  リリースに入れば大きな価値を生む。
  → Mustと合わせて80%以内が目安。

Could（あれば嬉しい）
  余裕があれば入れる。なくてもリリースは成立する。
  → スプリントの余白に入れる程度。

Won't（今回はやらない）
  今回のスコープには含めないことを明示したもの。
  「将来的にやるかもしれないが、今回は対象外」も含む。
  → これを明示することがスコープ管理の核心。
```

**分類に迷ったときの問い**

- Mustに入れようとしているとき: 「これがなければリリースできないか？本当に？」
- Should / Couldの区別に迷うとき: 「リリース後にユーザーから最初に聞かれそうなのはどちらか？」
- Won'tに入れることを躊躇するとき: 「今回やらないと決めると何が困るか？困らないならWon'tでよい」

---

### Step 3｜スコープの負荷チェック

分類が終わったら、Mustの量がリソースに対して現実的かを確認します。

```
Mustの工数合計 ≦ 利用可能な工数 × 0.7
```

0.7をかけるのはバッファのためです。予期しない問題・レビュー・修正が必ず発生します。

Mustが多すぎる場合は、以下の順で対処します。

1. **MustをShouldに降格できないか検討する**（「本当にMustか？」を再問する）
2. **Mustの中で分解できるものがないか検討する**（「最小限の実装で価値を届けられないか？」）
3. **リリース日を調整する**（最後の手段）

---

### Step 4｜スコープ定義表の出力

以下の形式でスコープ定義表を出力します。

```markdown

**作成日**: YYYY-MM-DD  
**対象リリース**: [リリース名・バージョン]  
**リリース予定日**: YYYY-MM-DD  
**想定工数**: [エンジニアN人 × N週]

---

## Must（必須）
このリリースで必ず届けるもの。

| # | 項目 | 理由 | 工数見込み |
|---|---|---|---|
| 1 | | | |

|---|---|---|---|

```

---

### Step 5｜Won'tの扱いを明示する

Won'tリストは単なる「やらないもの」の捨て場ではありません。以下を必ず伝えます。

- **なぜ今回やらないのかの理由を書く**。理由がなければ、後で「なぜ入っていないのか」という議論が再発します。
- **関係者への事前共有を推奨する**。「入ると思っていたのに入っていない」という期待のズレは、リリース直前に発覚すると最もコストが高いです。
- **Won'tは「永遠にやらない」ではない**。「今回のリリースでは対象外」という意味です。将来の検討余地を残します。

---

## 注意事項

- **Mustは少なく保つ**。「全部Must」になったとたん、スコープ管理の意味がなくなります。Mustは本当に必須のものだけに絞ります。
- **Won'tを怖がらない**。スコープを守ることはプロジェクトを守ることです。Won'tの理由を丁寧に説明できるようにしておきましょう。
- **スコープは変わる**。一度決めたスコープも、新しい情報が入れば見直して構いません。ただし変更は明示的に行い、関係者に伝えます。

---

## 参考：よくある失敗パターン

**失敗① MustとShouldの区別がない**  
症状: 「全部Must」「全部重要」になる。  
対処: 「これがなければリリースを中止するか？」という問いをMustの基準にする。YESと言えるものだけがMustです。

**失敗② Won'tリストを作らない**  
症状: スコープに入らなかったものが暗黙のうちに消える。後で「あれはどうなった？」となる。  
対処: Won'tは必ず明示する。「今回はやらない」と書くことで、関係者の期待値を揃えます。

**失敗③ スコープを決めた後に追加し続ける（スコープクリープ）**  
症状: 「これも追加して」が重なり、Mustが膨らみ続ける。  
対処: 追加する場合は「何かを外す」をセットにする。スコープの総量を一定に保ちます。
