# Skill 4｜仕様書 → 指示プロンプト

## このSkillの目的

仕様書の内容を、AIへの実装指示プロンプトに変換します。コードを書かずに動くプロトタイプを得るための最終ステップです。

**インプット**: 仕様書（Markdown形式）  
**アウトプット**: AI実装指示プロンプト（そのままAIに貼り付けて使えるもの）

---

## 実行手順

### Step 1｜仕様書の読み込みと確認

仕様書を受け取ったら、プロンプト生成に必要な情報が揃っているかを確認します。

**最低限必要な情報**
- 何を作るか（概要）
- 誰のための機能か（対象ユーザー）
- ハッピーパス（正常系の操作フロー）
- 使用技術スタック（不明な場合は確認する）

**なくても進めるが、あると精度が上がるもの**
- エッジケース・例外処理
- 表示状態の定義（ローディング・エラー・空状態）
- UI/UX仕様の詳細

技術スタックが不明な場合は必ず確認します：「どの技術スタックで実装しますか？（例：Next.js + TypeScript、React、Pythonなど）」

### Step 2｜指示プロンプトの生成

以下のテンプレートで指示プロンプトを生成します。

```
## Goal
<!-- 「〇〇というユーザーが〇〇できる機能を作る」の形式 -->

## Tech Stack
- 言語: 
- フレームワーク: 
- その他ライブラリ・ツール: 

## Requirements

### 機能要件
1. [機能名]
   - [具体的な要件]
   
2. [機能名]
   - [具体的な要件]

### エッジケース・例外処理
- 〇〇の場合 → 〇〇する
- 〇〇がエラーの場合 → 〇〇を表示する

### UI状態の定義
- デフォルト: 
- ローディング中: 
- エラー時: 
- 空状態: 
- 成功時: 

### やらないこと
- 〇〇は実装しない
- 〇〇は対応しない

## Output
出力形式:
- ファイル構成:
- コードの形式（コピペで動く状態にすること）:
- コメント: [日本語/英語/不要]

## Constraints
- コードは動作確認済みのものを出力すること
- ライブラリのインストールが必要な場合は手順を明記すること
- 不明な点があれば実装前に確認すること
```

### Step 3｜プロンプトの品質チェック

生成したプロンプトに対して以下を確認します。

**チェックリスト**

- [ ] GoalにユーザーとPurposeが含まれているか
- [ ] Tech Stackが具体的に書かれているか
- [ ] エッジケースが漏れていないか
- [ ] やらないことが明示されているか
- [ ] Output形式が指定されているか

**プロンプトの品質を上げるTips**

- **具体的であるほど良い**。「いい感じのUI」ではなく「ボタンはdisabled状態にして、ローディングスピナーを表示する」と書く。
- **やらないことを書く**。AIは指示がなければ機能を追加しようとする。スコープを守るために明示する。
- **一度に全部頼まない**。複雑な機能は「まずデータ取得部分だけ実装して」のように分割する方が精度が上がる。

### Step 4｜完成版の出力

完成した指示プロンプトをコードブロックで出力します。

必要に応じて、分割して渡すことを推奨します：
- 機能が多い場合：「機能ごとに分けて渡すことを推奨します」
- UIが複雑な場合：「まずロジックだけ実装させて、次にUIを当てる順番が安定します」

---

## 注意事項

- プロンプトはAIへの仕様書です。仕様書と同じくらい丁寧に書きます。
- 指示が曖昧なプロンプトは、曖昧なコードを生成します。「なんとなく動くもの」ではなく「検証できるもの」を目指します。
- プロトタイプの目的は完成品を作ることではなく、仮説を検証することです。完璧を求めず、検証に必要な最小限の実装を指示します。
